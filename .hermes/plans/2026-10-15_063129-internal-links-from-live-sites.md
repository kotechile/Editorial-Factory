# Internal links: obtained from the live sites, stamped for a shared CMS — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.
> **Revision 4 (2026-10-15) — the already-published articles must be repaired after all.**
> Rev 3 was forward-only because the owner had fixed the existing links *in the front end*. He has since
> established that this does not survive: the fronts are static builds that render the CMS body verbatim,
> so the next rebuild from the CMS reinstates every bad anchor. **The durable copy is the WordPress post
> content, and that is what has to be corrected** — Part C, §2.6. Unchanged: no vertical/routing changes,
> the split happens at the front end (aichieve.net pulls articles from selected categories), and the
> corpus comes from the fronts rather than from WordPress.
> **Cron fleet is PAUSED (2026-10-15, giniloh.com / aichieve.net split)** — nothing here needs a cron
> run; changes take effect on the next resume.

**Goal:** (a) obtain internal-link candidates from each reader site's own live content instead of from
WordPress, and (b) stamp the links in the article body in a form that stays *internal* whichever
frontend serves the article under the new pull model.

**Architecture:** a new `scripts/site_corpus.py` owns "what is live on site X" (sitemap discovery →
per-page metadata → disk cache → classification). `scripts/build_internal_link_index.py` becomes a thin
assembler that keeps the existing `context/internal_links.json` candidate shape and *adds* per-site
paths. A new `scripts/frontends.py` resolves, for any article, **which frontends will serve it** and
**which frontends serve a candidate page** — both derived from the frontends' own sitemaps, no new
owner-maintained registry. `scripts/internal_links.py` then stamps eligible links as **site-relative
paths** instead of one site's absolute URLs. WordPress leaves the link path altogether: it no longer
proposes candidates and it no longer reports a diff (§2.4).

**Tech stack:** Python 3.11 stdlib only (urllib, json, re, html, hashlib, concurrent.futures) — no new
dependencies. Bash + `verify.sh` for gates.

**1.3 The candidate index cannot see aichieve.net at all.** `build_internal_link_index.py:132-160`

## 2. Design

### 2.1 Obtain — the corpus comes from the sites

```
context/frontends.json (NEW, 3 rows)          public.vertical_sites (UNCHANGED — routing only)
   domain, frontend_url, url shapes                 vertical → destination site + wp_category_id
        │                                                     │
        ├──────────────► scripts/site_corpus.py ◄──────────────┘ (destination = ranking preference only)
        │                 discover_sitemaps()  robots.txt → /sitemap.xml → /sitemap-index.xml → recurse
        │                 fetch_page()         cached, polite, canonical-verified
        │                 page_metadata()      JSON-LD → og:* → <title>/<h1>
        │                 classify()           article | category | tool | skip
        ▼
context/internal_links.json    candidates: {site, kind, slug, title, url, path, sites_live{},
                               category_slugs, categories, category_ids, excerpt, modified, live}
```

The three reader fronts live in `context/frontends.json` (a 12-line file) rather than in
`vertical_sites`, because the owner is not changing routing and because `vertical_sites` *cannot*
express aichieve.net (it is a pull target, not a publishing destination). Routing keeps its one job:
ranking preference and the CMS category a draft is filed under.

**Served categories are derived, not declared:** the `/categories/<slug>/` hubs a frontend publishes in
its own sitemap are the categories it serves (`frontends.served_categories()`), so aichieve.net's pull
set is read from aichieve.net. If the owner later pins the set explicitly in `frontends.json`, the
pinned value wins — one optional field, no code change.

### 2.2 Stamp — the form that survives the pull

For the article being written, `renderers(article)` = the frontends whose `served_categories()` contains
the article's category hub slug; empty/unknown falls back to the vertical's routed site (today's
behaviour, so nothing regresses before a pull is configured).

A candidate is **eligible** iff its relative path resolves on **every** frontend in `renderers(article)`
— a pure set-intersection over the per-site URL sets already fetched, no extra requests. Eligible links
are stamped as **site-relative paths**, so the same stored body is internal on every frontend that
renders it, and stays internal when the pull set changes:

```markdown
## Related reading

- [70% of Agent Failures](/agent-failures-tests-stayed-green/)
- [$250k AI Upkeep Tax](/enterprisebuildvsbuy-the-250k-ai-upkeep-tax/)
```

Why relative and not a CMS-host absolute URL: the frontends' rewrite (`/root/giniloh/src/lib/wordpress.ts:166-182`)
only touches hrefs pointing at *its own* configured CMS base; aichieve.net is a different deploy and I
cannot verify its rewrite from here. A relative path needs no cooperation from any renderer — it is
already what giniloh's rewrite emits, and every article path on both fronts is the same shape
(`/slug/`). It is also correct on the CMS itself (WordPress permalinks are root-level `/slug/`), though
`/categories/<slug>/` is front-end-only (a CMS preview would 404 that one — noted, not a reader surface).

Targets whose path **differs** between renderers (giniloh `/calculators/gpu-compute/` vs aichieve
`/tools/gpu-compute/`) are dropped for a multi-renderer article rather than stamped wrongly. The
existing contract already allows a zero-link outcome and states the gap, so no new failure mode appears.

Everything else about the block is unchanged: anchor text from the target's title, the
two-subject-token evidence bar, same-site scoring preference, idempotent delimiters, the gap note.

### 2.3 Two consumers to keep honest

- `scripts/sitemap_sync.py` maps a live article slug → its public reader URL by reading
  `internal_links.json`. Adding aichieve.net candidates introduces a second row for the same slug for the
  first time, and that file is **not modified**: the existing "first candidate for the slug wins" scan
  keeps answering with the routed site because the new rows are appended after it (Task 9 proves this on
  the real index rather than assuming it).
- `scripts/growth_os.py:285` compares `routing["wp_category_id"]` (int) against `candidate["category_ids"]`
  (WP term ids). Page metadata yields a hub *slug*, not an id — so the category axis becomes
  name→slug, reusing the primitive already in the file (`own_hub`, `growth_os.py:300-304`), with
  `category_ids` kept in the JSON for back-compat so existing tests keep passing.

### 2.4 Scope boundary

Parts A and B (the corpus and the stamping) change only what is generated **from now on** — no published
artifact is rewritten and no reader URL is re-pointed by them (§2.5 proves it). Repairing what is already
published is **Part C** (§2.6): deliberately a separate, reviewable pass over the CMS.

Still out of scope, deliberately:

- The 85 slugs published on both giniloh.com and aichieve.net, and their missing `rel=canonical`
  agreement — a canonicalisation question, not a link question.
- CMS↔frontend liveness mismatches as a class: rev 2's advisory coverage diff
  (`check_cms_site_coverage.py`) stays dropped; Part C reports what it touches and nothing more.
- `public.vertical_sites`, verticals, cron schedules, CMS categories, `scripts/sitemap_sync.py`.
- Front-end code (rev 1's Part B is withdrawn): the fix has to be durable in the CMS, so a render-time
  rewrite is explicitly *not* the mechanism.

### 2.5 The forward-only guarantee, and how it is proved

The change alters two things: **which pages are candidates** (front ends instead of the CMS) and **what
form a stamped link takes** (relative path, gated on the render set). Neither can reach backwards, and
that is asserted, not assumed:

| Must not change | Why it cannot | Proof (Task 9/11) |
|---|---|---|
| An already-published artifact's block | Nothing rewrites `published/*.md`; the generator runs only inside a push | `git status --porcelain published/` empty after a full rebuild; byte-compare 5 named artifacts |
| `context/sitemap.json`'s reader URL per article | New aichieve rows are appended after the routed site's row; the file's scan is first-match | before/after diff of the reader-URL map over the current corpus |
| Any CMS post, Supabase row, or front-end build | The only writes in scope are `context/internal_links.json` + `.md` | `wp_draft.py`/`publish.py` are untouched; no deploy step exists in this plan |
| Vertical routing | `public.vertical_sites` is read-only throughout | Task 7's tests run against fixtures; no upsert code added |

If a proof fails, the change is wrong — not the guarantee. The one behaviour that legitimately differs is
the *content of links generated from now on*, which is the entire point.

### 2.6 Part C (rev 4): repair the anchors already inside the CMS bodies

**Why the front-end fix is not durable.** The fronts are static builds that render the CMS body verbatim
(plus a rewrite of their *own* CMS host). A front-end patch dies on the next rebuild from the CMS, and
what the reader sees comes back. Measured on `aichieve.net/your-cluster-hidden-clock/`: three
`giniloh.com` anchors plus a self-link, served straight out of its CMS post content.

**What is repaired inside a body, and what is not:**

| Class | Action |
|---|---|
| The generated `## Related reading` block (ours, delimited) | Regenerate from the current corpus (`scripts/internal_links.py`) — stamped relative, gated on the render set |
| An inline anchor to a **sibling** front whose path resolves on every front that serves the article | Rewrite to that site-relative path |
| A sibling anchor whose path resolves on only some of them (giniloh `/calculators/x/` vs aichieve `/tools/x/`) | Leave byte-identical, report it — one relative path cannot be right on both |
| An anchor to a retired page (in no front's sitemap) | Leave byte-identical, report it. Deleting reader-visible text is the owner's call: on 2026-10-01 a "cleanup" pass deleted reader copy from a row and re-pushed the shortened body, and the delivery check could not see it because it compared the payload against the CMS |
| An anchor to the serving front's own pages | Leave — already internal and correct |
| Everything else in the body (prose, images, tables, schema) | Untouched, byte for byte |

**Render set for a CMS body:** the fronts publishing the article's category hub (`hub_slugs` in
`context/internal_links.json`), exactly as the generator resolves it. A hand-written post has no Supabase
row and no vertical, so its render set falls back to the fronts whose sitemaps list its slug
(`sites_live`) — where it is actually served, measured rather than assumed.

**Write path — reuse, never invent:**

- `wp_draft.WordPress._call("POST", f"posts/{id}", {"content": html})` — **content only, never a `status`
  field** (sending `status=draft` unpublishes a live post: post 401, 2026-10-01).
- `WordPress.find_by_slug(slug)` to resolve the post; `DB.update_body(...)` to write the same body back to
  Supabase so the row and the CMS cannot disagree (the repo's standing invariant).
- **Read-back verification after every write**: re-fetch the post, assert zero sibling-front anchors
  remain, and assert the diff is exactly the intended substitutions.

**Safety rails:**

- `--dry-run` is the default; `--apply` writes; `--post <id>` / `--limit N` for a small batch.
- **Byte-diff assertion per post**: stripping the intended substitutions from the new body must restore
  the original byte-for-byte, and the `<a ` count must be unchanged. That is what turns "we only touched
  the URLs" into a check instead of a claim.
- A post needing no change is **never written** (no gratuitous CMS revisions); a second run reports
  nothing to do for every post.
- Candidates are only posts carrying a sibling-front anchor or a stale generated block.

left; **the byte-diff invariant**; idempotency (a second pass changes nothing); the generated block is
replaced by the block pass rather than edited in place; reader prose is never touched.

#### Task C3: the write path + read-back verification

**Files:** Modify `scripts/fix_cms_links.py` (add `--apply`).

Per post: build the new body, PATCH `content` only, re-fetch, assert zero sibling anchors and the
byte-diff invariant, then write the matching Supabase row. A failed assertion is reported as a failure,
never as a success.

#### Task C4: dry-run the small batch and get the owner's nod

Print the before/after anchors for the 5 worst posts (his standing preference: an inspectable batch before
anything fleet-wide). No writes until he says go.

#### Task C5: apply, then prove it from the reader side

Apply in batches of ~10, re-reading after each; then, once the fronts rebuild, re-run Task C1's audit
against the **rendered** pages and require zero sibling-front anchors — a CMS write is only half the proof
and the front end is the surface the reader sees.

## 6. Risks and tradeoffs

- **Relative anchors change what the CMS stores.** The draft/published body will carry `/slug/` instead
  of an absolute URL. Verified consequences: correct on both fronts (both use root-level article
  paths), correct on the CMS itself for articles (WP permalinks are root-level), front-end-only for
  `/categories/<slug>/` (a CMS preview would miss that one — not a reader surface). Reversible per
  article by re-running the generator after a revert.
- **A target live on one front only is dropped, not stamped.** For aichieve-pulled articles that means
  fewer offered links (today's giniloh-only calculator links are ineligible). That is the honest
  outcome — a link that 404s or leaves the site is worse than no link — and the block already states the
  gap when it comes up empty.
- **`served_categories` derived from a sitemap is a proxy** for the frontend's actual pull rule. It is
  the frontend's own published output, so it is the closest observable signal; the plan allows pinning
  it in `frontends.json` the moment the owner sets the pull explicitly.
- **A stale sitemap lies.** Liveness is decided by the sitemap, so a page can outlive its post until the
  frontend rebuilds (observed 2026-10-05 on wellroost). `--check`'s re-read of the live sitemaps is the
  net; Task 3's canonical guard catches the "removed, answering with the shell" case.
- **No behaviour change until the fleet resumes.** Fine and intended.
- **`not_live` weakens if the CMS is unreachable** (it becomes silent rather than wrong — it can only
  add a warning, never a candidate). It is kept for the artifact/diff surfaces that read it; it is not
  extended and no new mismatch is surfaced from it (owner decision, §2.4).

## 8. Rollout & rollback

Order: Tasks 1-4 (modules + tests, no behaviour change) → 5-6 (rebuild; diff old vs new JSON offline
before shipping) → 7-9 (consumers) → 10-11 (cron wiring, docs, gates).

The fleet is paused for the split, so there is no window pressure. The rebuild is idempotent and the
previous path stays in git history: rollback = `git revert` + `python3 scripts/build_internal_link_index.py`.
`context/.site_cache/` is disposable — deleting it costs one cold crawl (~200 requests).

**Part C ordering (rev 4):** C1 audit → C2 rewriter + tests → C3 write path → **C4 dry-run of the 5 worst
posts, then the owner's nod** → C5 apply in batches, re-verify each, then re-crawl the fronts. The fronts
can change mid-flight (they did: giniloh.com's sitemap went 1,148 → 1,072 URLs while rev 3 was being
verified), so C5 re-reads them rather than trusting an earlier snapshot.
