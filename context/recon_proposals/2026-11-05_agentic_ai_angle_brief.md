**Signal B (Anchor 2):** Signed, Sealed, Leaked: Trust Beyond Signature for MCP Toolchains, 2026-11-04 — (https://arxiv.org/abs/2611.06585). A legitimately signed tool that performs its advertised function while concealing code that leaks confidential information; Meta's MCPGuard-Dynamic blocks a direct exfiltration in the same run yet fails to prevent this attack in every trial; germline execution records no unauthorised disclosure across 153 attack runs against 5.9%–74.5% for baselines and an ablation; every runtime completes 99/99 benign steps; 10–49 ms per single-copy call, 2–28x faster than restarting the tool per invocation.
**Signal C (design leg, context):** MCP specification, Security Best Practices (document version 2025-06-18) — (https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices). The protocol's own threat model for local servers is install-time — a malicious startup command in a client configuration, a payload distributed inside the server, DNS rebinding against an insecure local server — and the stated mitigation is consent before execution plus sandboxing.

**Emergent Collision Point:** The two anchors answer different questions about the same object and neither crosses the other's line. Signal A builds the ecosystem's first dependency census and tags each capability by provenance (directory-claimed or live-probed) — an audit surface made of *identity and capability*. Signal B shows a correctly signed release from the authentic publisher can still hand data to a destination the policy allows, so identity and capability are both silent on the only thing that leaked: what data each invocation carried. The paper's own comparison puts the point sharply — each baseline binds authority to a different object and misses a different vector; output labels miss carry-over and laundering, and confinement misses disclosure through permitted destinations. The emergent claim is that the unit of MCP trust has to move from the artifact to the invocation, and the inventory an architect would build from MCP-Eco is not the inventory that answers the question. The second half is the cost: the control that held was forking a data-free process per call, and it is cheaper than the conventional state-clearing reset, so the boundary is not a tax.
**Hook:** An inventory of 9,200 MCP configuration declarations now exists, and 5,975 of them resolve to a server project — but a signed tool from an authentic publisher leaked in 74.5% of the attack runs where only signature and key pinning were enforced, and the defence that reads as state of the art failed every trial of the same attack.
**Tension:** The ecosystem is being measured at the level of repositories and declared capabilities (directories, live probes, dependency graphs) while the control that failed is at the level of a single call's argument set. Vendors are shipping the identity layer — signature verification, pinned keys, allowlisted destinations, eBPF confinement — and those are exactly the layers the paper's matrix shows leaking 5.9% to 74.5% of runs. Whoever builds the tool gateway inherits a policy that cannot see the data it authorises, and a dependency census that will never show it.
