**Signal A (Anchor 1):** How Much Can Tool Calls Reveal About You? Privacy Leakage from Tool-Call Traces (Duan, Liu, Liu, Zou, Hu, Liu), 2026-10-30 — (https://arxiv.org/abs/2610.41885). PrivacyTrace: 1,000 synthetic user profiles, 4,000 agent trajectories, four domains, real MCP tools from 25 servers; four mainstream LLM attackers reach a 26.25% profile-inference success rate against 17.97% from prior-based guessing; tool arguments and returned results are the main trace-grounded evidence, and linking traces across sessions amplifies the risk.
**Signal B (Anchor 2):** What Standard Evaluations Hide About Detectors of Hijacked LLM Agents: Rare Attacks, Unseen Tools and Benchmark Transfer (Abbasi, Núñez V., Shahraki), 2026-10-30 — (https://arxiv.org/abs/2610.41803). Eleven audited evaluations place attacks or anomalies at 16%–86% of test samples, none varies that share, six test no second benchmark; at a 2% attack rate a detector with AUROC 0.879 reaches precision 0.076, with the negative mix alone moving it between 0.039 and 0.117; rankings cross near 50% tool coverage and reverse below it; no AgentDojo transfer above chance (0.47–0.52); the released monitor reaches 0.930 across benchmarks but its decision rule still lands at precision 0.096 at 2%.
**Signal C (third leg):** Log-To-Leak (Hu, Fan, Samyoun, Du), 2026-10-26 — (https://arxiv.org/abs/2610.36108). Across 18 model-server pairs with valid tool execution the attack reaches 62.64%–100% success and 76.55%–95.64% conditional logging accuracy while 16 pairs move target-task completion by at most 6.63 points; three defenses leave residual success above 55% on GitHub MCP with GPT-4o; an instruction detector flags 85.53% of benign descriptions.
**Signal D (platform primitive, context):** OpenTelemetry GenAI semantic conventions for MCP, repository `docs/gen-ai/mcp.md` — (https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md). MCP spans carry `mcp.method.name`, `mcp.session.id`, `mcp.protocol.version` beside `jsonrpc.request.id`, and the conventions define client and server session-duration metrics.

**Emergent Collision Point:** The two papers measure opposite halves of one asset. Signal A shows the trace is rich enough to identify the person behind it from arguments and returned results alone — no conversation needed — and that joining sessions sharpens the profile. Signal B shows the same trace is too thin to identify an attacker: at the base rate where a hijack detector would actually run, its high discrimination score converts into alarm precision in the single digits, and it fails on tools it never trained on. Neither paper states the consequence, because each treats the trace as its own object: the record is a **regulated data store** with a security use, not a **security control** that happens to hold data. That inversion changes the architect's decision from "which detector do I buy" to "what do I retain, redact, join and authorize at the trace layer" — and Signal C shows the same channel carries an exfiltration path that leaves the task outcome intact, so the trace cannot be trusted on the evidence of a green task either.
**Hook:** Two papers posted the same day measure the trace layer from opposite ends: an attacker can infer who a user is from MCP tool-call traces 26.25% of the time, and a hijack detector scoring AUROC 0.879 falls to 7.6% precision at a 2% attack rate. The record you keep as your security control is both a profile of your customer and a weak alarm.
**Tension:** The observability market is standardising the trace, not shrinking it: OpenTelemetry's MCP conventions now stamp a session identifier on every tool span, and platform vendors sell trace-level injection detection as a feature. So the surface is getting richer, the join keys are getting standardised, and the detection numbers that justify the spend are measured at 16%–86% attack shares — base rates no production fleet sees. Whoever owns the trace store inherits a privacy obligation and a detection claim, and the two are not the same budget.
