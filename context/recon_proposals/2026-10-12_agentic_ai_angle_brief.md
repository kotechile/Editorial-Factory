**Signal A (Anchor 1):** "One Skill Too Many: How Co-Installed Skills Conflict in Coding Agents" (2026-10-08 — https://arxiv.org/abs/2610.11647). Mined from 20,947 repository snapshots: 822,109 candidate similar-skill pairs, 3,754 judged, 1,639 confirmed, 312 confirmed pairs run on three models — 6,368 runs, 169,294 tool calls, 542 agent-hours. A similar co-installed skill takes one in five runs away from the installed skill (its use falls 19.9 percentage points, against 5.9 points when an unrelated skill is added) and fidelity on its exclusive core functions falls 5.6 points, while task completion does not drop. The final reply names the skill that ran in only 0.9% of substituted runs, and the conflict is decided at the first read of a skill — 97% of runs change no file before it — where a pre-tool hook switched the model back in 96% of cases.
**Signal B (Anchor 2):** "Understanding and Mitigating Cross-Session Attacks via Persistent Artifacts in Agent Skill Composition" (2026-10-09 — https://arxiv.org/abs/2610.13227). SkillRelayBench: 270 adversarial cases from 30 cross-session skill-composition scenarios across ten domains, evaluated on seven models running Codex CLI, Gemini CLI and Claude Code — attack success rate 46.7%–77.4%, attack chain success rate 35.6%–61.1%, and the agent finishes the user's task while also achieving the attacker's objective in 53.0% of evaluations. SkillRelayGuard — read-time provenance restoration plus a pre-execution advisory review — cuts attack success from 69.5% to 10.9% and chain success from 54.8% to 10.0% while raising legitimate task success from 79.6% to 87.5%, at 4.3% of total tokens.
**Emergent Collision Point:** Both studies break the same assumption that skills are passive, static instructions, and both find the damage invisible to the only metric most teams watch. Signal A measures a namespace problem inside one installation: a co-installed look-alike skill hijacks the run, the installed skill's guardrails are dropped, and task completion never moves — so a green test certifies the wrong thing. Signal B measures a persistence problem across installations in time: files, configs and cached data a skill writes in session one are read by a different skill in session two, so two attacker-controlled packages can relay an instruction, widen a data boundary or poison the evidence base without ever touching the same session. Neither paper states the other's finding, and their fixes converge on the same architectural control point rather than on the model: guard the first read, restore artifact provenance at read time. Collided, the thesis is that the skill layer has become stateful infrastructure — a dependency set with no lockfile and an inter-session state channel with no ownership — and reliability work that stays inside the prompt, the model or the completion metric is aimed at the wrong layer.
**Hook:** Two studies published a day apart measured 6,368 controlled coding-agent runs and 270 adversarial cross-session cases, and both found the same thing: the agent's own task-success check cannot see the damage. In one, a similar installed skill displaced the installed one in a fifth of runs and dropped the guardrails only the installed skill carried, with task completion flat. In the other, 53% of successful attacks ended with the user's task completed.
**Tension:** Skill installation is treated as configuration and distributed as a package ecosystem, but the studies show it behaves like a dependency graph with shared mutable state. That turns three ordinary practices into exposures: installing a second skill that does the same job, letting a skill write files or caches the next session will read, and gating a release on task success. It helps the architects who own the harness layer and can spend control at the read boundary; it threatens the "swap the model" line item and the benchmark score that holds the tool and skill environment constant.
**Target reader:** ai_architect
**Single claim to defend:** For a long-horizon coding agent, the skill layer — which package wins, and what state survives between sessions — decides whether the guardrails hold, and both failure classes are decided at read time and invisible to task success, which is why the fix belongs at the read boundary.
