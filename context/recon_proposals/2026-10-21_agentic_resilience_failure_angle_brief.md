**Angle Type:** Synthesis (Cross-Topic Fusion)
**Winner:** Isolation Isn't Detection: the containment architecture shipping in production is validated on failures that announce themselves, while the failure class that halves agent success arrives with no signal — and nobody in the centre is allowed to read the value
**Scores:** E=9.0 A=9.0 S=9.5 → Composite=9.2 (0.35·9.0 + 0.30·9.0 + 0.35·9.5 = 9.175)
**Signal A (Anchor 1):** Meta Engineering, "The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do", 2026-10-19 — a 1,300-line orchestrator routing 20+ workflows to 14 specialist agents that "performs zero domain work itself"; the single-agent predecessor scored "70-80% *with* manual prompt engineering per task … Without that handholding, success dropped to 10-20%"; the reliability property claimed is containment — "If a subagent fails, the orchestrator retries or escalates. The failure doesn't corrupt the orchestrator's state or other subagents' contexts" — and the orchestrator's own gate checks "for active warnings or required reviewers", with steps 1–5 and 7 deterministic and only delegation left to a model. (https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent/)
**Signal B (Anchor 2):** arXiv:2610.27777, "RITE: Evaluating End-to-End Resilience to Silent Tool Errors in E-Commerce Agentic Systems", submitted 2026-10-20 — a silent error is "a plausible but incorrect value to be returned without an explicit failure signal"; across 167 matched units in nine workflows (501 instances) and 10 recent LLMs, "silent errors roughly halve task success and are consistently harder than explicit failures"; the share of rollouts that notice the bad value at all runs "from 0.208 to 0.336", the latest observation still matches the polluted value in 57.8% of the rollouts that did notice, and recovery scores 0.387 without refetching the producer against 0.655 with it. (https://arxiv.org/abs/2610.27777)
**Emergent Collision Point:** Meta's architecture is a blast-radius argument, and its reliability claims are all stated over failures that fail: a subagent errors, the orchestrator retries or escalates, the blast radius stays inside one worker. RITE measures the class where nothing fails: the tool returns a schema-valid, plausible, wrong value, which ten current models notice in 20.8%–33.6% of rollouts. Containment does not touch that value — it preserves it, cleanly, inside a worker whose whole design premise is that it never sees the other subsystems. And the centre cannot catch it either, because the orchestrator "performs zero domain work" by design and its reliability gate is procedural (warnings, reviewers), not semantic. Neither source can state the fusion: Meta reports what isolation does to a loud failure; RITE reports that the dominant failure is quiet and that noticing it is a separate, measurable capability. Read together, the thin orchestrator moves the failure surface rather than shrinking it — from a central agent that poisons everything to fourteen specialists that each ship a wrong value with nobody left in a position to read it. Which relocates the control: a state check on the returned value at the tool boundary, owned by the layer that can compare it against the workflow, not by the router and not by "the model will notice".
**Hook:** Meta cut configuration prep for a new data column from three or four days by hand to under an hour by taking all domain reasoning out of its orchestrator, and it says why the system is reliable: "Failures are contained." The same day, a benchmark built from industrial e-commerce workflows found that the failure which costs ten current models roughly half their task success is one where nothing fails at all — a tool hands back a plausible wrong value, and only 20.8% to 33.6% of rollouts notice.
**Tension:** Two reliability programmes are moving in opposite directions and both are being adopted. The platform side has concluded that context is contamination: give one agent all the domain knowledge and, past a threshold, "additional knowledge *degraded* rather than improved performance" — so split it into isolated specialists, keep the router deterministic, and contain failure to one worker. The evaluation side has just measured what a split system inherits: silent, schema-valid corruptions that survive the split intact, that the isolated worker has the least context to question, and that the router is architecturally forbidden from reading. The party that gains is whoever owns the value boundary — the tool adapter, the workflow step, the state checker — because that is the only place with both the value and the expectation. The party that is exposed is every team that reads "failures are contained" as "failures are caught", and every team whose observability stops at whether a call succeeded.
**Target reader:** infra_engineer
**Single claim to defend:** Containment bounds failures that announce themselves, and the measured dominant failure in agent workflows is one that does not — a schema-valid wrong value, unnoticed in roughly two-thirds to four-fifths of rollouts by ten current models, invisible to a router that does no domain work and to a specialist isolated from the context that would make it look wrong — so detection has to be built as a state check on the returned value at the tool boundary, and noticing is not enough on its own: recovery only improves when the agent refetches the producer (0.387 → 0.655), which is why the check belongs in the harness rather than in the prompt.
