# Evergreen Brief: agentic_ai — 2026-11-12
**Archetype:** evergreen

**Decision the reader is facing:** How many agents to place on one host, and how the runtime should release their turns — whether to provision CPU from the mean the box reports (or from the GPU share it is paired with) or from the tail of the host-side tool phase that actually sits on the request's critical path, and whether every ready turn is submitted the moment it becomes ready.
**Durability:** The mechanism is structural and outlives any model generation: an agent request alternates model turns with host-side tool stages, so the host is on the critical path, container CPU is handed out in fixed quota slices, and a scheduler that releases work eagerly builds a queue it can no longer reorder. The measured figures are dated snapshots a reader can re-check — the characterization **as of** arXiv:2608.04458v1 (5 Aug 2026, Azure fleet study plus four open-source frameworks), the release-scheduling study **as of** arXiv:2609.10964v1 (10 Sep 2026), the CFS period default **as of** Docker's current resource-constraints documentation, and the retry-budget example **as of** the 2017 SRE book — while the three rules they feed (size from the tool tail, release under a work budget, pool cores by role) do not expire.

**Thesis:** An agent request is a burst, not a steady stream — the host-side tool phase interrupts every model turn, host CPU on one traced run sits near an 11% median and rises to nearly 100% at stage boundaries, and a container's cores are metered in 100-millisecond quota slices — so a runtime provisioned from average CPU (or from its GPU share) converts its own tool burst into p95, and the three levers measured to fix that are a released-work budget instead of eager release (workflow P95 flow time down up to 71.4%, a 3.5x speedup under contention, at parity under light load), cores pooled and pinned by role (tool CPU demand down up to 46%, worst-case tool latency 13% better, 99% of serving throughput retained), and reclaimed idle cores (95% of a co-located workload's standalone throughput at under 3% slowdown) rather than a bigger static box.

## Notes (verbatim anchors for the drafting pass)
- **The burst sentence, which cannot carry a gate row and must be carried in prose under row 1** (arXiv:2608.04458v1, §IV-A, Fig. 5 discussion): "Host CPU utilization stays near its 11% median during the sequential portions, but rises rapidly to nearly 100% at these stage boundaries. This contrast between average and peak demand makes static provisioning inefficient." The same section's Fig. 12 is captioned "Per-request tool-call frequency by category (average and P99)", and the paper's own sentence about it reads: "the tail is far heavier than the average and behaves distinctly across functional categories" — that is the licence for "size from the tail of the tool count", but it states no digit, so it rides in prose, not in a row. Do not invent an average-vs-P99 tool count; the paper prints it only inside the figure.
- **Critical-path sentence** (§I): "As orchestration and tools run on the host, the CPU sits on the critical path." And (§IV-A): "the host-side tool phases account for a substantial fraction of the end-to-end latency. The CPU therefore becomes part of the critical path for agentic requests instead of merely feeding the accelerator." Qualitative — prose only.
- **The three fixes are the same paper's §V**, so the article may not present role pooling or core harvesting as a different vendor's claim: §V-A CPU harvesting ("recovers 95% of a co-located workload's standalone throughput", "+30% host CPU utilization", "agent slowdown to under 3%"), §V-A GPU harvesting ("frees a third of the GPUs", "+82% generation throughput", "tail latency by 2.5x"), §V-B role-aware pooling ("tools' CPU demand by up to 46%", "worst-case tool latency by 13%", "99% of serving throughput"). Note the units: the 46% is CPU *demand*, the 13% is *worst-case tool latency*, the 99% is *serving throughput* — three different quantities; do not merge them into one "46% faster".
- **Release scheduler, exact wording (arXiv:2609.10964v1):** "Most runtimes release each turn immediately upon readiness. Under contention, this eager release policy can accumulate released but unfinished work; once submitted, those turns can no longer be reordered by the workflow-level policy, increasing tail latency." Results: "up to a 71.4% reduction in workflow P95 flow time, corresponding to a 3.5x speedup", "performs comparably to eager release under light load". Its own controller starts the committed-work budget at 120,000 work units, bounded between 30,000 and 300,000, with queue-mean / queue-P95 targets of 1 s and 5 s and a starvation threshold of 180 s — usable as an illustration of *shape* (a bounded work budget adapted to queue pressure), never as a recommended setting.
- **CFS mechanism (Docker Docs):** "Specify the CPU CFS scheduler period, which is used alongside --cpu-quota. Defaults to 100000 microseconds (100 milliseconds). Most users don't change this from the default." and "Impose a CPU CFS quota on the container. The number of microseconds per --cpu-period that the container is limited to before being throttled." The kernel's own description (docs.kernel.org/scheduler/sched-bwc.html, fetched 2026-11-12, not a gate row because its default-value sentence collides with a `p(100)` token elsewhere on the page) adds the consequence: "Throttled threads will not be able to run again until the next period when the quota is replenished." Quote Docker for the row and attribute the replenishment sentence to the kernel docs in prose if used.
- **Retry budget (SRE book):** "Consider having a server-wide retry budget. For example, only allow 60 retries per minute in a process, and if the retry budget is exceeded, don't retry; just fail the request. This strategy can contain the retry effect and be the difference between a capacity planning..." — read the live page for the rest of that sentence rather than completing it from memory.
- **No hands-on claim.** This desk ran no hosts and measured nothing; every number above is cited, and the arithmetic the article performs (quota headroom, in-flight work) must be shown as arithmetic, not as a benchmark.
