**Signal A (Anchor 1):** NIST CAISSI, NSA SISC and CISA, "Key Practices for Incident Readiness and Response in Super Intelligence Training and Evaluation", published 2026-10-16 (PP-26-4396, Ver 1.0). Ten voluntary key practices in five stages. Practice 1.5, verbatim: "Limit SI agent network access, via a strict allowlist where possible. Route any required network access through a monitored gateway". Practice 3.3: "Ensure that SI agents cannot access or interfere with monitoring processes and logs". Practice 5.3 requires "tamper-resistant logs with reliable timestamps sufficient to reconstruct agent trajectories, tool calls, reasoning traces, user interactions, environmental states, and security-control decisions". (https://www.nist.gov/document/keypracticesforincidentreadinessandresponseinsuperintelligence-trainingandevaluation and https://www.nist.gov/news-events/news/2026/10/key-practices-incident-readiness-and-response-super-intelligence-training)
**Signal B (Anchor 2):** LiteLLM v1.107.0 release compromise, disclosed 2026-10-21 in the maintainer's own incident report. Malicious build on PyPI from 11:39 to 13:23 UTC and on the official container tags (v1.107.0, latest, main-latest, main-stable) from 11:46 to 14:20 UTC; "compiled malware which steals credentials and loads remote-code execution tools"; pushed through "three engineers' GitHub accounts, appearing to be by way of stolen GitHub CLI OAuth tokens"; "The compromised artifacts were built from an attacker-controlled repository". Datadog Security Labs: about 23 million weekly downloads, payload "targets cloud, developer, AI-tool, browser and LiteLLM proxy credentials". Microsoft: "A separate database module attempted to read selected credential and model-configuration records from the LiteLLM proxy", and "An application did not need to import LiteLLM for the payload to run". (https://docs.litellm.ai/blog/security-incident-oct-21-2026 and https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker)
**Emergent Collision Point:** The guidance's central architecture is concentration: one allowlisted egress, one monitored gateway, one place where every agent's traffic can be seen and stopped. LiteLLM is the most widely installed implementation of exactly that device, and it holds every upstream provider key by design. So the control the guidance recommends is also the highest-value credential store in the agent estate, and the month the guidance shipped, that store's release pipeline was hijacked — not its code, its build. Neither document states the trade the other creates: the guidance buys visibility by concentrating trust, and the concentration is what made one malicious build worth 23 million weekly downloads.
**Hook:** On 21 October, for 104 minutes, the Python registry served a backdoored build of the gateway that most enterprises put in front of their agents; five days earlier the federal guidance told them to put a monitored gateway in front of their agents.
**Tension:** The reader has been buying or building a chokepoint and treating its presence as the control. The incident says the chokepoint's own provenance is the control, and the guidance has no practice for it: practice 3.3 protects the monitors from the agents, not the monitors from their own supply chain, and practice 5.3 asks for tamper-resistant logs from a component that ran its payload at interpreter start, before any application log line existed.
**Target reader:** enterprise_cai
**Single claim to defend:** The monitored gateway is a concentration of both control and credential risk; governing agents therefore requires treating the gateway as a supply-chain dependency with its own provenance, pinning and egress rules — not as a control that arrives trusted.
