**Decision the reader is facing:** How long to let one agent tool call run, and who owns that number — the model that chose the tool, the wrapper that invoked it, or the runtime — before the harness calls it a failure and retries a call whose downstream p99.9 nobody on the team has measured.
**Durability:** The deadline is a structural property of an at-least-once call, not a model-version artifact: selecting a timeout from a stated false-timeout budget and reading the matching latency percentile is Amazon's published production practice (as of the June 2026 revision of the AWS Builders' Library note), the load-amplification arithmetic of independent per-layer retries is a fixed consequence of fan-out depth (243x in the same note), Temporal's documented default retry policy — 2.0 backoff coefficient, 1-second initial interval, 100-second maximum interval — is a contract of that engine (as of its current docs, retrieved 2026-10-12), Stripe's idempotency-key window is a documented API contract (24 hours, keys up to 255 characters, as of the docs retrieved 2026-10-12), and the measured agent-side figure is τ-bench's tool-agent inconsistency (under 50% task success, pass^8 under 25% in retail, arXiv v1 as of 2024-06-17). Only the per-service percentile numbers drift; the rule for choosing a deadline does not expire.
**De-dup:** The nearest prior artifacts for this vertical are 2026-10-07_durable-execution-not-a-transaction (the task's state footprint plus an effect's declared undo semantics carried across the tool boundary) and 2026-10-08_agent-failure-topology-not-model (read the failure shape before swapping the model); neither decides *the deadline* — how long a call may run, which failure is a false timeout, and what load a retry adds. This brief settles timeout selection and retry amplification per hop, a distinct evergreen beat with no prior artifact on it.
**Thesis:** A tool call's timeout is the one reliability parameter the model cannot set and cannot see: the harness must derive it from a stated false-timeout budget (accept 0.1%, read the downstream p99.9), because a deadline set from a round number converts slow success into a retry, and independently retrying layers multiply the load on a shared downstream — while the agents doing the retrying are measured to be inconsistent enough to retry on their own.
