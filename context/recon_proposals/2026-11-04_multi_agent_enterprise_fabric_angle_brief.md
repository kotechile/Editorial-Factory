# Angle Brief: multi_agent_enterprise_fabric — 2026-11-04

**Angle Type:** Synthesis (Cross-Topic Fusion)
**Winner:** The checkpoint nobody owns: 60.7% of destructive agent tools ask no one, and about 88,000 agent skills tell the agent to stop asking
**Scores:** E=9.0 A=9.0 S=9.0 → Composite=9.0

**Signal A (Anchor 1):** "When Neither Side Confirms: Destructive Tool Approval Across MCP Servers and Hosts" — submitted 2026-11-02 (https://arxiv.org/abs/2611.02527). Measured from source code on a 1,000-repository sample of the official MCP registry and 41 popular open-source hosts and agent SDKs: an estimated 90% of destructive tools (95% CI 82–95) carry no server-side confirmation; 32 of 41 hosts have no approval step by default, including 16 of 25 applications; 60.7% of destructive-tool/application pairs have no enforced human approval by default; through four agent SDKs, four of five low-cost models executed an injected deletion in 479 of 960 runs; prompting for every tool not annotated read-only or non-destructive would cut the unapproved share to 5.4%, while universal elicitation support alone would leave 56.7%.

**Signal B (Anchor 2):** "When Skills Tell Agents Not to Ask: A Large-Scale Study of Oversight Directives in Agent Skills" — submitted 2026-10-27 (https://arxiv.org/abs/2610.37734). Across 1.53 million English skills from GitSkills, about one in seventeen (about 88,000 skills) contains a directive that loosens oversight — proceed without approval, bypass checks with `--no-verify`, keep working without checking in; 70.1% of those directives apply unconditionally rather than only in a specific context such as CI; skills that run shell code, install packages or use sudo have 1.7–1.8 times the odds of carrying one, and do not compensate with more tightening language; 2.4% of skill families account for half of all copies of loosening-carrying skills, so the problem spreads through a few upstream packages rather than through edits by adopters.

**Emergent Collision Point:** Neither paper describes the checkpoint the way a governance review describes it. Signal A fixes the *boundary* axis: the protocol splits confirmation between server and host, each side waits for the other, and the measured default is that nobody asks. Signal B fixes the *instruction* axis: the reusable package an architect loads into the agent can delete the ask before the tool boundary is ever reached — and the packages most likely to do it are the ones with shell access. Multiply the two and a fabric's approval rate is not a policy property at all; it is a property of two artefacts nobody reviews together: the skill library a team curates, and the host's default prompt. That is the thesis neither paper states, because each measured its own layer in isolation. The number that makes it actionable is the counterfactual in Signal A: a host that prompts on anything not positively annotated read-only takes the unapproved share from 60.7% to 5.4%, while the protocol's own preferred mechanism (server-side elicitation everywhere) leaves 56.7% — so the fix is a *default at the host*, not a capability in the protocol.

**Hook:** A named platform engineer signs off a fabric review on the strength of a governance slide that says "human approval required for destructive actions". The measured defaults underneath that slide: 90% of destructive tools ship with no server-side confirmation, 32 of 41 hosts ship with no approval step, and one skill in seventeen that the team installed says proceed without asking.

**Tension:** The protocol's own text says there *should* always be a human able to deny a tool call, and that clients *must* treat tool annotations as untrusted — yet confirmation is a SHOULD for applications, an optional annotation for servers, and a decision the host makes silently. NIST's Tenet 05 arrives at the same control from the policy side (risk thresholds that trigger review, plus an explicit warning about consent fatigue) and Tenet 07 and 08 put the policy layer outside the model entirely. Meanwhile the vendors shipping enforcement points — Google's Agent Gateway, Agent Registry and per-microVM identity — attach at the network and identity layer, which is the layer that is *not* unconfigured. So the gap survives every control an enterprise has bought: the missing piece is a default in a config file, in a skill package, and in the sentence a team writes into a prompt when it wants the agent to stop asking.

**Target reader:** `ai_architect`
**Single claim to defend:** In an agent fabric the human approval is not a model capability or a protocol guarantee but a default set in three separate artefacts — the skill package, the server's annotation, and the host's prompt configuration — and on the measured defaults of each, none of them fires; the approval rate a firm actually runs is therefore a property of the packages and hosts it installed, not of the policy it wrote.
