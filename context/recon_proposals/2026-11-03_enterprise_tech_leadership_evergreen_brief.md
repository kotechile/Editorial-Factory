**Durability:** The load-bearing content is arithmetic and a counting rule, not a price, a version or an incident: a PostgreSQL connection is a server process with its own memory, `work_mem` is an allowance *per sort or hash operation inside one session*, so the memory ceiling is connections × operations × `work_mem`, and a pool's size is multiplied by the number of application replicas that open it — none of which changes when the instance class or the pooler vendor changes. **Thesis:** A database connection is not a cheap handle but a process holding a memory allowance that multiplies per query operation, so the real connection ceiling is set by the instance's memory and the `work_mem` you allow — not by `max_connections` — and because every application replica opens its own pool, a default pool size copied from a library turns the replica count into a multiplier that exhausts the database after the code ships, which makes pool size and pool mode architecture decisions to be set in review rather than library defaults.
