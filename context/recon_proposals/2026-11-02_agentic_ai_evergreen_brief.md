# Evergreen Brief: agentic_ai — 2026-11-02
**Archetype:** evergreen
**Vertical:** agentic_ai
**Persona:** ai_architect
**Decision the reader is facing:** Where the runtime puts its concurrency limit when the fleet saturates — per request, per session, or per tenant — what to cap it against (request rate, token quota, or KV-cache budget), and how many sessions one serving instance may hold before the queue starts billing the reader in tail latency rather than in throughput.
**Durability:** The arithmetic is queueing, not model version: a session that issues N dependent calls holds a prefix in cache for its whole life, so the scheduler's unit of admission decides how much reuse it keeps and how long it waits behind its own siblings — the same trade in twelve months, whatever model sits above it. The measured spread (4-15x program throughput, **as of** arXiv:2502.13965v1, 19 Feb 2025), the production trace shares (77.7% cached input, 78.4% decode duration, 34.7% fewer instances, **as of** arXiv:2609.33224v1, 27 Sep 2026), the load curve (192 sessions → more than 17x generation time, **as of** arXiv:2603.18897v3, 16 Jun 2026) and the quota arithmetic (80% cache hit × 2,000,000 ITPM → 10,000,000 effective input tokens, **as of** the provider page read 2026-11-02) are dated snapshots a reader can re-check; the admission rule they feed does not expire.
**De-dup:** `2026-10-29_your-sandbox-boot-tax-110x-then-nothing` is this vertical's nearest prior artifact, four days old, and it prices a *fixed provisioning cost per trajectory* (boot time amortised over N actions) — how expensive one session is to start. This brief takes the session's start-up as given and decides *how many sessions may be live at once* and what the runtime caps them against, which is a different quantity: concurrency against a cache budget, not boot against action count. `2026-10-12_agent-timeout-false-alarm-budget` sets a per-call timeout threshold and says nothing about how many calls may be in flight; `2026-10-15_agent-loop-bound-not-a-budget` bounds steps inside one session; `2026-10-26_your-tool-boundary-costs-3-engineers` counts deployed boundaries, not concurrent sessions. Cross-vertical checked and dropped by hand: `2026-10-08_cache-boundary-decides-input-bill` (enterprise_ai_finops) decides where the cache breakpoint sits *inside one prompt* to shrink the input bill, never how many sessions share a cache; `2026-10-22_your-agent-team-loses-28-points` prices a multi-agent team against a single agent, assuming the queue is free. A whole-corpus grep of `published/` and `context/recon_proposals/` for `admission control`, `head-of-line`, `KV cache`, `session concurrency` and `scheduler` returns no artifact arguing where the concurrency limit belongs, so this is not a retread in this corpus or another vertical's.

**Thesis:** A runtime's capacity is held by sessions, not requests, so the number an architect must cap is concurrent sessions per instance against a KV-cache budget — and three independent measurements agree from different directions: scheduling programs instead of calls is worth 4-15x program throughput at equal latency because a request-level queue blocks a session behind its own siblings (and 5.5x over the preemptive request-level alternative on mixed workloads); a production agent trace runs on 77.7% cached input tokens, so a session that loses its prefix pays twice — in prefill, and against a token quota that an 80% cache-hit rate is documented to multiply five-fold; and the damage under load lands on generation, where 192 concurrent sessions stretched generation time by more than 17x while the tool side, 45%-57% of end-to-end latency, barely moved. The trap is buying latency by starting more work: the same study's controlled experiment doubled tool speed under high load and the extra returning work absorbed the gain back into the GPU, which is why the cap has to sit at admission and the latency has to be bought on the tool side.
